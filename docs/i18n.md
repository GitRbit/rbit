# Languages and installable language packs

Localization is an optional embedded plugin. Enable or disable **Languages** at
**Admin → Plugins** without restarting repository hosting. English is built into
`rbit-messages` and remains usable without the plugin, its catalog parser, or any
installed language pack.

## Install and use a pack

1. Open **Admin → Plugins** as a site administrator.
2. Choose a `.rbit-language` ZIP from a publisher you trust and select **Install language pack**.
3. Enable **Languages** and choose **Language** in the footer. Signed-in choices are saved
   for the account; anonymous choices are saved in an HttpOnly, SameSite browser cookie.

Packs can be installed while Languages is disabled. Installation parses and validates data;
it runs no scripts or package hooks. An active installation/update publishes a complete new
catalog snapshot only after validation and durable storage succeed. Removing a pack changes
new request resolution immediately. Removing a pack required as another pack's parent is
refused until its dependent pack is removed or replaced.

Disabling selects English for new requests, removes the language picker, and releases the
published catalog provider. Installed packs, user preferences, and ordinary repository data
remain stored. Re-enabling restores available preferences. Existing renders keep their
original immutable snapshot so their text, language, direction, and response metadata agree.
These snapshots are data, not permission grants; the admin request that disables the plugin
cannot deadlock waiting for its own render lease.

Installing a higher version of the same package ID updates it. A version identifies immutable
content: changed bytes require a higher version, and downgrades are refused. Reinstalling the
same archive is idempotent. A damaged stored archive can be replaced by a higher version or
removed while the provider is disabled. A failed provider starts in English with diagnostic
status so administrators can repair language data without taking the forge offline.

Translations can change sign-in, security and administrator instructions. The administrator
is authorizing trusted core/Actions language data, not verifying a publisher signature.
Publisher names are descriptive; SHA-256 checksums detect content corruption, not publisher
identity. Catalog values always render as escaped text. Host templates own links and markup.

## Example packs and authoring

The repository includes three reproducible examples in [language-packs](../language-packs):

- `es.rbit-language`: a partial Spanish starter pack. Untranslated messages fall back to English;
  this example is not a claim of complete linguistic review.
- `en-XA.rbit-language`: accented, expanded pseudolocalization for layout checks.
- `ar-XB.rbit-language`: an RTL pseudolocale for direction and layout checks, not an Arabic translation.

Regenerate them with `python3 scripts/build-language-packs.py`; verify reproducibility with
`python3 scripts/build-language-packs.py --check`. The shared message inventory is
[`catalog.json`](../crates/rbit-messages/src/catalog.json). IDs are namespaced `core` or
`actions`; protocol field names, Git refs, status keys, user content and stored identifiers
are never translated. Argument types are part of the host schema.

The manifest is `pack.toml` at the archive root. Catalogs are UTF-8 Fluent files below
`catalogs/`, and a license file must be listed. For example:

```toml
schema = 1
id = "language.es"
version = "1.0.0"
locale = "es"
direction = "ltr"
message_schema = "^1.0"
publisher = "Your language team"
license = "MIT"
license_file = "LICENSE.txt"

[catalogs]
core = "catalogs/core.ftl"

[checksums]
"catalogs/core.ftl" = "<lowercase SHA-256 of the exact catalog bytes>"
"LICENSE.txt" = "<lowercase SHA-256 of the exact license bytes>"
```

Fluent supports text, named typed arguments, select expressions, grammatical plural
categories, and bidirectional isolation. The deliberately bounded implementation rejects
message/term references, attributes, executable functions, and arbitrary formatters.
`NUMBER`/`DATETIME` and a complete CLDR date/number formatting API are not offered by this
phase. See the [engine format gate](../crates/rbit-i18n/README.md) for the exact profile.

Packs use canonical supported language/script/region tags, not arbitrary private locale
extensions. A declared `parent` must be a present same-language pack; catalog fallback is
exact locale, declared parent, then English. Conflicting providers for the same locale and
namespace are rejected; installation order never silently selects a winner. The UI reports
validated message counts against the schema at installation, with English fallback for gaps.

The ZIP32 profile is intentionally narrower than a general ZIP extractor: no directory
records, extra fields, comments, descriptors, ZIP64, executable entries, links, encryption,
absolute/traversing paths, duplicate or unlisted files. Use the example builder as a packaging
reference. The host does not extract archives to filesystem paths.

## Limits and persistence

Limits include 2 MiB compressed per archive, 8 MiB expanded, 512 KiB per entry, 128 entries,
4,096 messages per pack, bounded AST depth/nodes and an 8 KiB formatted result. At most 64 packs
may be installed; active expanded data and aggregate message counts also have bounded totals.
Formatting arguments and browser negotiation are bounded before evaluation. The source
constants and adversarial tests document the limits precisely.

Migration `0062_language_packs.sql` adds package metadata/archive BLOBs and independent account
locale preferences. Pack writes and metadata updates are transactional. SQLite backups include
these authoritative bytes without invoking an enabled provider or copying a live directory
of package files. Old migration files are unchanged. Active catalogs are parsed once and read
from immutable memory, with no per-message SQL, filesystem access, or IPC.

## Locale and cache identity

Resolution uses account preference, anonymous/browser cookie, bounded `Accept-Language`, then
`[i18n] default_locale`. Unsupported saved preferences remain recorded and fall back safely.
HTML uses the same snapshot for messages, `lang`, `dir`, `Content-Language`, and the
`Rbit-Locale-Revision` header. Normal API payloads and runner RPC are unchanged.

Non-English HTML varies on the actual preference inputs, is private and revalidated, and
does not retain commit-pinned immutable HTML caching. Built-in English preserves the existing
30-second preload window and immutable commit fragments, with locale revision in their
representation key; normal account writes do not churn those immutable entries. Catalog identity includes a boot-unique
revision, so a browser cannot reuse an old shell/catalog identity after a server restart.
Catalog changes during rendering trigger a fresh navigation rather than publishing mixed
metadata. Raw Git data, highlighting and hashed asset caches remain locale-independent.

Changing language forces a full navigation, retires preload/history, and refreshes the
anonymous offline fallback without discarding it when the network is unavailable. The same browser profile broadcasts observed locale changes to other tabs. Remote
admin changes are discovered on the next network response; existing in-memory preloads can
remain visible for their existing bounded freshness period (30 seconds). This is revision
invalidation, not an instant cross-browser push notification service.

## Distribution and configuration

The normal binary includes the optional engine but starts it disabled:

```toml
[i18n]
enabled = false
default_locale = "en"
```

Persisted administrator intent overrides `enabled` across restarts. Other deployment settings
require restart. A distribution without the i18n feature rejects effective enabled intent;
explicit persisted disablement permits startup even when the deployment default enables it.
Disable the provider before moving an enabled instance to a core-only distribution.

```sh
# Both implementations, neither starts merely because its code is included.
cargo build --release -p rbit-server
# Keep only localization support.
cargo build --release -p rbit-server --no-default-features --features i18n
# Keep the forge and built-in English, without either optional implementation.
cargo build --release -p rbit-server --no-default-features
node scripts/check-core-dependencies.mjs
```

This phase localizes shared chrome, static core/Actions presentation, literal view titles,
Actions status/event labels, common error pages, and selected browser enhancements. Dynamic
service validation prose, server human-time strings and email delivery still retain English
where no typed presentation message has been introduced. These are explicit further conversion
work, not a dependency on the optional provider. Independently installable executable plugins,
third-party message namespaces and untrusted-code isolation are later platform work.

## Validation and performance

CI covers no optional implementation, Actions only, i18n only, and both. It checks catalog
references, reproducible example packs, unsafe archives/Fluent, deterministic fallback,
plurals/RTL, replacement/disable/restart, persisted preferences, authorization/Origin, backup
inclusion, cancellation of HTTP waiters, and browser cache transitions.

`rbit-i18n` has an ignored manual release benchmark for 1,000 warmed pages of 100 interpolated
messages. One local run measured a mean of 27.49 microseconds per page; it did not collect p95
and is not an end-to-end latency guarantee. The disabled English path borrows fixed labels
and sends no browser translation dictionary. Use the documented benchmark on deployment
hardware before asserting an application latency budget.
